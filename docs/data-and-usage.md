# 데이터 구조, 전송량, 사용량

## 데이터 구조
- Connector는 `--interval`(기본 10초)마다 측정하지만, **업로드는 `--upload-every`(기본 3분)마다 한 번**만 합니다. 그 사이의 측정값은 PC 안에서 평균을 내고, 현재값과 끝난 1분 평균(필요하면 1시간 평균)을 요청 **한 건**에 묶어 보냅니다.
- `latest/<기기>`: 현재값. `m/<기기>/<날짜>`: 1분 평균(2일 보관). `h/<기기>/<월>`: 1시간 평균(100일 보관). 오래된 데이터는 Connector가 스스로 지웁니다.
- 업로드가 실패하면 끝난 구간을 PC에 쌓아 두었다가 다음 성공 때 함께 보냅니다(오프라인 뒤 자동 보충). 기본 방식(여러 경로를 한 번에 쓰기)이 거부되면 경로별 쓰기로 자동 전환합니다.
- 숫자는 반올림해서(CPU·부하 소수 2자리, 나머지 정수) 요청 크기를 고정합니다.
- 15분~24시간 보기는 분 평균, 7일·30일 보기는 시간 평균을 읽습니다. 대시보드는 이미 받은 구간은 다시 받지 않고 **새로 생긴 구간만** 받아 이어 붙이며, 탭이 숨겨지면 갱신을 멈춥니다.


## 전송량 (컴퓨터 1대 기준 업로드)
아래는 이 프로젝트에서 **직접 측정한 크기**(요청 본문, HTTP/2 오버헤드, 새 연결 비용, 인증 토큰 갱신 등)를 합산한 계산입니다. 실제 Firebase에서 잰 값은 아니므로 ±20% 정도 다를 수 있고, 값은 Connector가 센 네트워크 연결 위의 바이트(IP/TCP 헤더 제외, 실제 회선에서는 약 5~10% 더)입니다. 다운로드(받은 양)는 포함하지 않습니다.

| 업로드 간격 | 연결이 유지될 때 (한 달 30일) | 연결이 매번 끊길 때 (한 달) |
|---|---|---|
| 1분 | 하루 0.90MB · **27MB** | 하루 4.3MB · 128MB |
| **3분 (기본)** | 하루 0.58MB · **17.5MB** | 하루 1.7MB · 51MB |
| 5분 | 하루 0.52MB · 15.6MB | 하루 1.2MB · 35MB |
| 10분 | 하루 0.47MB · 14.1MB | 하루 0.8MB · 24MB |

- **기본(3분)에서 컴퓨터 1대당 한 달 약 17.5MB, 5대면 약 87MB**입니다. 구성은 업로드 480회 × 약 1KB(본문 약 0.9KB + 헤더 약 70B) = 약 486KB, 인증 토큰 갱신(1시간마다) 약 70KB, 긴 주소 재전송 약 19KB, 시간 단위 기록과 정리 약 8KB입니다(하루 합계 약 583KB).
- **"연결이 유지될 때"**는 HTTP/2 연결이 업로드 사이에 열려 있어서 헤더가 몇 바이트로 줄어드는 경우입니다. Connector는 연결을 최소 5분 유지하지만, 서버가 그보다 일찍 닫으면 "매번 끊길 때"에 가까워집니다. 어느 쪽인지는 실제 서비스에서만 알 수 있으므로 "업로드 총량"으로 확인하세요.
- 가장 큰 영향은 **연결 유지 여부**(약 3배)와 **업로드 간격**입니다.


## 압축과 연결 재사용
업로드 데이터를 줄이기 위해 다음을 하고 있습니다. 측정값은 이 저장소의 테스트로 확인할 수 있습니다.

| 방법 | 효과 | 상태 |
|---|---|---|
| **HTTP/2 헤더 압축** | 업로드마다 같은 긴 주소(인증 토큰 포함)를 보내는데, HTTP/2에서는 두 번째부터 몇 바이트로 줄어듭니다. 요청의 본문 외 오버헤드가 939B에서 69B로 줄었습니다. | 자동 (서버가 HTTP/2를 지원하면) |
| **연결 유지** | 업로드 간격보다 오래 연결을 열어 둡니다. 같은 업로드가 유지된 연결에서는 592B, 연결이 닫혀 있었다면 2,909B였습니다(새 연결의 암호화 협상 비용). | 자동 (최소 5분, 업로드 간격의 2배) |
| **값 반올림, 쓰기 응답 생략** | 숫자를 짧게 하고, 서버가 쓴 데이터를 되돌려 받지 않습니다. | 자동 |
| **대시보드 파일 압축** | 사이트의 JS·CSS는 호스팅이 압축해서 전달합니다. | 자동 (제가 아는 호스팅 동작) |
| **업로드 본문 gzip** | 한 번에 보내는 본문(현재값+분 평균 3개)이 약 930B에서 약 350B로 **약 62% 줄었습니다**(값이 분마다 달라지는 실제와 같은 데이터로 측정). 같은 키가 반복되기 때문입니다. | **실험 옵션** `--compress` (기본 꺼짐) |

`--compress`가 기본으로 꺼져 있는 이유: Realtime Database가 압축된 **요청** 본문을 받는다는 공식 문서를 찾지 못했고, 오래된 Firebase 답변에는 클라이언트가 전송 데이터를 압축하지 않는다는 내용이 있었습니다. 실제로 Firebase **에뮬레이터는 압축된 업로드를 415(지원하지 않는 형식)로 거부**했습니다. 그때 Connector는 설계대로 같은 데이터를 압축 없이 다시 보냈고 데이터는 유실되지 않았습니다. 실제 서비스도 같을 가능성이 높아서, 이 옵션은 큰 기대를 하지 않는 것이 좋습니다. 서버가 거부하면(400/415) 로그에 "does not accept compressed uploads"를 남기고 이후로는 압축하지 않습니다. 켜 보고 싶다면 "업로드 총량"으로 효과를 확인하세요.

위 "전송량" 표의 "연결이 유지될 때"는 HTTP/2 헤더 압축과 연결 재사용을 가정한 값입니다. 실제 서비스에서 적용되는지는 몇 시간 돌린 뒤 "업로드 총량"으로 직접 확인하세요.


## 컴퓨터별 업로드 총량 표시
각 컴퓨터의 Connector가 Firebase로 **실제로 보낸 데이터량**을 직접 세어서 대시보드에 보여 줍니다. 개요 화면의 "업로드 총량" 타일(전체 합계), **노드** 표의 "업로드" 열(총량과 최근 24시간), 노드 상세의 같은 타일에서 볼 수 있습니다. 받은 데이터량도 함께 셉니다.

- **무엇을 세나**: 네트워크 연결(소켓)에서 오간 바이트입니다. 암호화와 프로토콜 오버헤드가 포함되고 IP/TCP 헤더는 빠지므로, 통신사 청구 기준 사용량보다 3~5% 정도 적게 나올 수 있습니다. 로컬 Netdata에서 읽는 데이터는 세지 않습니다.
- **정확도**: Connector가 센 값과 별도로 만든 측정 프록시의 요청 바이트 합계를 비교했을 때 **0.0% 차이**였습니다(에뮬레이터 환경).
- **기준 시점**: 등록한 뒤부터의 누적이고, 몇 분 늦게 반영됩니다. 값은 Connector의 설정 파일에 저장되어 재시작하거나 PC를 껐다 켜도 이어서 쌓입니다(종료할 때와 1분마다 저장). 설정 파일을 지우고 다시 등록하면 0부터 다시 셉니다.
- **최근 24시간**: 1시간 단위 기록에 남겨 둔 누적값과의 차이로 계산합니다.
- **이 기능이 생기기 전의 Connector**로 등록한 컴퓨터는 "–"로 표시됩니다. 새 Connector로 교체하면 그때부터 셉니다. 이 값은 Firebase 콘솔의 사용량(다운로드 기준 한도)과는 별개의 참고용 값입니다.
- 이 기능을 쓰려면 규칙을 다시 배포해야 합니다(`node firebase/deploy.mjs`가 함께 처리합니다).


## Spark 한도
- 제가 아는 Spark 한도는 DB 저장 1GB, **다운로드 월 10GB**, 동시 접속 100입니다. 5대 기준 저장량은 수 MB입니다. 업로드(쓰기)는 한도에 들어가지 않고, Connector가 쓰기 응답을 되받지 않도록(`print=silent`) 설정해 두었습니다.
- 한도는 바뀔 수 있으니 [요금제 페이지](https://firebase.google.com/pricing)에서 확인하세요. 한도를 넘으면 청구되지 않고 해당 기능이 일시적으로 막힙니다.
